Deploying a service ⁠#

Everything a team needs to move a service from a laptop to production, in the order the steps have to happen.

A deployment is three decisions: where the code runs, when it moves, and who is told. The rest of this page is about the first one, and it assumes you have already read the prerequisites.

Prerequisites ⁠#

  • An account with deploy permission on the target project.
  • The command line tool, installed with npm i -g @acme/cli.
    • Version 4 or later.
    • Authenticated once with acme login.
  • A service definition committed to the default branch.

A deployment that cannot be reversed is not a deployment. It is a migration, and it needs a different review.

Running it⁠#

Press Ctrl then C to stop the watcher before you start.

acme deploy --env production --wait
  ✓ built in 14s
  ✓ 3 instances healthy
  1. Build the image.
  2. Push it to the registry.
  3. Roll the instances, one zone at a time.
Environments and their gates
Environment Approval Rollback window Notified
development none — nobody
staging automatic 1 hour the owning team
production two reviewers 24 hours the owning team and the on-call rota
Zone
One failure domain. A roll never touches two at once.
Gate
A condition that has to hold before the next zone starts.
What happens when a gate fails

The roll stops where it is. Instances already replaced keep serving, and the ones behind the gate stay on the previous revision until somebody decides.

Deprecated flags are struck through in the reference: --fast became --no-wait in version 4. Terms are marked on first use, like blue-green, and SLO targets are checked at each gate.1
